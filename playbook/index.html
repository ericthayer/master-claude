01Getting started with Claude

Learn how Claude works, how to brief it like a teammate, and which features matter most for design work.

About 25 minutes · 4 parts

What Claude is, and how to think about it

Claude is an AI model made by Anthropic. You talk to it in everyday language, and it writes, reasons, reads images, and builds working code. There are no special commands to learn.

The most useful way to think about Claude is as a fast, well-read collaborator who has never seen your project. It knows a lot about interface patterns, HTML and CSS, accessibility, and writing. It knows nothing about your users, your constraints, or your taste until you tell it. What you get back depends mostly on how well you brief it.

Treat Claude likeNot like
A collaborator you brief with contextA search box you type keywords into
A teammate who drafts fast while you directAn oracle that makes design decisions for you
A partner you iterate with over several messagesA vending machine that should nail it in one try
A sharp reviewer whose work you double-checkA source of truth you never verify

You'll find Claude in the browser at claude.ai, in the desktop app for Mac and Windows, and in the mobile apps. This playbook uses four building blocks, introduced as you need them:

  • Chats for back-and-forth work on one topic.
  • Projects to keep instructions and reference files attached to every chat.
  • Artifacts for live previews of the pages, documents, and diagrams Claude makes.
  • Claude Code for building with real files on your computer.
Tip

Keep one topic per chat. Claude remembers everything earlier in the same conversation, which is great when you're iterating on one prototype and confusing when you switch to something unrelated. Start a fresh chat for a new topic.

Writing prompts that work

A prompt is the message you send Claude. You already know how to write a good one, because a good prompt is a design brief. It sets context, states the task, names the constraints, and describes the deliverable. Here's one, annotated like a spec.

Do and don't

Instead ofMake a login page.

Why it works: it names the audience, the exact elements, the visual direction, and the quality bar, so Claude doesn't have to guess.

Instead ofIs this design good?

Why it works: "good" is subjective. A named framework and a clear output make the feedback specific enough to act on.

Instead ofWrite some copy for the empty state.

Why it works: options, limits, and a tone give you something to choose from instead of something to fix.

Instead ofaccepting the first answer, or starting a new chat when it's off

Why it works: iterating keeps everything Claude has already learned in the conversation. Say what to keep as well as what to change.

Habits of good prompters

  • Attach screenshots. Claude can read images, so show it the Figma frame or live page you're talking about.
  • Ask it to ask you. End a big request with "Before you start, ask me any questions you need answered."
  • Say your skill level. "I'm new to HTML, so explain what each part does" changes the whole answer.
  • Ask for options. Three directions with trade-offs beat one answer you have to argue with.
  • Change one thing at a time. Small, specific follow-ups are easier to judge than a full rewrite.
  • Give it a role when it helps. "Review this as a senior accessibility specialist" focuses the feedback.

02GitHub setup guide

GitHub is where your portfolio files will live online. It keeps every version of your work and can publish your site for free. You can do everything here in your browser, with no terminal.

About 45 minutes, hands-on · 5 parts

Git in plain English

Git is a tool that tracks changes to files. GitHub is a website that stores Git projects online so you can back them up, share them, and publish them. Think of Git as version history and GitHub as the cloud it syncs to. Each term below comes with its closest Figma equivalent.

Repository (repo)

A project folder that remembers every change ever made to it.

In Figma: a file with its version history built in.

Commit

A saved snapshot of your changes, with a short note about what changed.

In Figma: naming a version in version history.

Push

Sending your new commits from your computer up to GitHub.

In Figma: your edits syncing to the cloud.

Pull

Bringing the latest commits from GitHub down to your computer.

In Figma: reopening a file and seeing a teammate's changes.

Branch

A parallel copy where you can try something without touching the main version.

In Figma: creating a branch of a file to explore.

Merge

Bringing a branch's changes back into the main version.

In Figma: merging a branch back into main.

Clone

Downloading a linked copy of a repository to your computer so you can work on it and sync back.

In Figma: opening a file in the desktop app.

README

The front page of a repository that explains what it is and how to use it.

In Figma: a cover page.

Tip

main is the name of your repository's default branch. Your live website will publish from it. For your first few weeks, working directly on main is completely fine.

Create your GitHub account

0 of 5 done
  1. Go to github.com/signup.

    Use an email address you'll keep for years. A personal address is safer than a work one.

  2. Choose your username carefully.

    It becomes part of your free website address, username.github.io. Your name, or something close to it, looks most professional.

  3. Verify your email.

    GitHub sends a code to your inbox. Enter it to finish creating your account, then choose the Free plan.

  4. Turn on two-factor authentication.

    Go to Settings → Password and authentication. An authenticator app on your phone is the simplest option, and GitHub will ask you to set this up anyway.

  5. Fill in your public profile.

    In Settings → Public profile, add a photo, your name, a one-line bio, and a link to your portfolio or LinkedIn. Recruiters do look.

Set up your first repository

A repository holds your site's files. You'll create one, then add a homepage, all in the browser.

0 of 6 done
  1. Start a new repository.

    Click the + in the top-right corner of GitHub and choose New repository.

  2. Name it username.github.io.

    Use your exact GitHub username. This special name gives you the cleanest web address. Any other name, like portfolio, also works; your site will then live at username.github.io/portfolio.

  3. Keep it Public and add a description.

    Free GitHub Pages hosting needs a public repository. Something like "My UX design portfolio" is a fine description.

  4. Add a README, then create it.

    Turn on Add a README file and click Create repository.

  5. Create your homepage file.

    Click Add file → Create new file. Name it index.html, all lowercase, and paste in the starter code below.

  6. Commit it.

    Click Commit changes, write a short message like "Add homepage", and confirm. That was your first commit.

What each part does

  • <!DOCTYPE html> tells the browser this is a modern web page.
  • <head> holds information about the page that isn't shown on screen.
  • <title> is the text on the browser tab and in search results.
  • <style> holds CSS, the rules for color, type, and spacing.
  • <body> holds everything visitors actually see.

Optional: work from your computer with GitHub Desktop

Editing in the browser is a fine way to start. When you want to edit files on your computer, or let Claude Code edit them, install GitHub Desktop. It's a free app that turns Git into buttons.

  1. Download it from desktop.github.com and sign in with your GitHub account.
  2. Choose File → Clone repository, pick your portfolio repo, and choose a folder such as Documents/portfolio.
  3. Edit the files in that folder with any editor.
  4. Back in GitHub Desktop, write a short summary of what changed, click Commit to main, then click Push origin.

Prefer typing commands? These three lines in a terminal do the same thing. Lines starting with # are notes for you; the computer ignores them.

Publish your portfolio with GitHub Pages

GitHub Pages turns your repository into a public website for free. Once it's on, publishing is automatic.

0 of 5 done
  1. Open your repository's settings.

    In your repo, click the Settings tab, then Pages in the left sidebar.

  2. Choose where to publish from.

    Under Build and deployment, set Source to Deploy from a branch.

  3. Pick the branch and folder.

    Choose main and the / (root) folder, then click Save.

  4. Wait a minute or two, then refresh.

    A message appears at the top of the Pages screen with your live address, such as https://username.github.io.

  5. Visit it and share it.

    From now on, every commit to main updates your live site automatically, usually within a couple of minutes.

Troubleshooting

Seeing a 404 page? Check that your file is named exactly index.html and sits at the top level of the repo, not inside a folder. Wait a few minutes, then hard-refresh with Cmd + Shift + R (Mac) or Ctrl + Shift + R (Windows). Images missing? File names are case-sensitive online, so Hero.png and hero.png are different files.

Tip

Want your own domain, like yourname.design? Buy it from any domain registrar, then add it under Settings → Pages → Custom domain. GitHub's documentation covers the DNS settings, or you can ask Claude to walk you through them.

Let Claude walk you through it

Stuck, or prefer a guided version? Paste this into Claude. It will go one step at a time and explain each action.

Follow-ups for when you get stuck

  • I got this error: [paste the error message]. What does it mean, and how do I fix it?
  • Here's a screenshot of what I see [attach screenshot]. What should I click next?
  • Explain what this file does, line by line, as if I've never seen code: [paste code]

Claude Code in the desktop app or VS Code

Claude Code is Claude working inside a folder on your computer. It can create and edit files, preview pages, and run Git commands for you. It asks before it changes anything, so you stay in control. Pick one of two ways to use it.

The Claude desktop app

Easiest for most designers

Open the Code tab and choose your portfolio folder (the one you cloned with GitHub Desktop). Then describe what you want in plain language, the same way you would in a chat.

VS Code

Best if you want to see the code

Install VS Code, open Extensions (Cmd + Shift + X), search for "Claude Code", and install it. Click the Claude Code spark icon in the editor toolbar and sign in with your Claude account.

Later, if you get comfortable with the terminal, you can also run Claude Code there. The official setup guide covers Windows and other options.

Try this as your first Claude Code prompt. It only reads, so nothing changes yet.

Heads up

Commit your work before asking for big changes, so you can always go back. Read each permission request before approving it. Claude tells you exactly which file it wants to change or which command it wants to run.

Browser and design-tool connections

Claude in Chrome

A browser extension that lets Claude see the page you're on and take actions you approve, like clicking through a sign-up flow and noting the friction.

  1. Install "Claude" from the Chrome Web Store and sign in.
  2. Pin it to your toolbar so it's one click away.
  3. Open any page, open Claude, and ask: "Review this page for usability and accessibility issues."
Heads up

Keep it away from banking, health, and other sensitive sites. Claude asks before important actions, but you're responsible for what happens in your browser.

Connectors for Figma, Google Drive, Notion, and more

Connectors link Claude to other apps. They're built on MCP (Model Context Protocol), an open standard, so new ones appear regularly.

  1. In Claude, open Settings → Connectors.
  2. Browse the directory and click Connect on the tools you use, such as Figma.
  3. Sign in to that app and approve access.
  4. In a chat, turn the connector on from the + menu when you need it.

With Figma connected, you can paste a link to a frame and ask Claude to build it in HTML or check it against your design system. No connector? Export the frame as a PNG and attach it. That works well too.

Save and reuse your prompts

Good prompts are design assets. Save them like components so you never write the same brief twice.

  • Keep a prompt library in your repo. Create a prompts.md file in your portfolio repository. It's versioned, searchable, and always next to your work. The Starter Kit in Frame 05 makes a good first version.
  • Put repeated context in a Project. Anything you'd type at the start of every chat, like who you are, your brand, and your skill level, belongs in Project instructions.
  • Turn routines into Skills. A Skill is a saved set of instructions Claude loads when a task calls for it, such as "write a case study using my structure". Find Skills in Claude's settings, or ask Claude to help you write one.
  • Use text shortcuts. On a Mac, System Settings → Keyboard → Text Replacements lets you type ;case and get your full case-study prompt. Raycast and TextExpander do the same with more features.

05Your reusable Claude workflow

A repeatable routine for prototyping, feedback, documentation, and research, plus a Starter Kit of 18 prompts worth keeping close.

About 15 minutes, then ongoing · 4 parts

The five-step loop behind every task

Almost everything you do with Claude follows the same five steps. When a result disappoints, it's usually because one of them got skipped.

  1. Brief

    Context, task, constraints, and format. Attach a screenshot.

  2. Generate

    Let Claude draft. Ask for options when you're exploring.

  3. Review

    Test it in a browser, at phone width, and with a keyboard.

  4. Refine

    Change one or two things at a time. Say what to keep.

  5. Ship

    Save it to your repo with a clear commit message.

Then repeat for the next change

Daily workflows

Four routines that cover most of a designer's week. Each comes with prompts you can copy.

Generate and iterate on HTML prototypes

  1. Brief with a description or a screenshot of the Figma frame.
  2. Generate a single-file prototype as an Artifact.
  3. Review it at desktop and phone widths. Click everything.
  4. Refine with targeted change requests, one or two at a time.
  5. Save the final code to your repo and commit it.
  • Give me 3 layout variations of this screen. Variation 1 should [direction], 2 should [direction], and 3 should [direction]. Keep the content the same so I can compare.
  • Keep everything exactly the same except [the change]. Then list what you changed.
  • /impeccable polish [page, e.g. the homepage]

Get design feedback and accessibility audits

  1. Share the screen as a screenshot, a link, or code.
  2. Ask for structured feedback against a named framework, like Nielsen's heuristics or WCAG 2.2 AA, or run a design skill that has one built in.
  3. Decide which points you agree with. You're still the designer.
  4. Recheck only what changed after you fix it.
  • /impeccable critique [page, e.g. the homepage]
  • Use the ui-ux-pro-max skill to review [page] against its UX guidelines and accessibility rules. List issues by severity with a fix for each, then refine [the area, e.g. spacing and color] to address the top three.
  • Act as [persona]. Try to [task] on this screen and narrate every moment you hesitate or feel unsure.
  • Here's the updated version. Recheck only the issues you raised before and tell me which are fixed.

Write UX documentation and case studies as you go

Five minutes of notes at the end of a work session saves hours when it's time to write the case study. Keep a running journal in your Project.

  • Here's what I did today on [project]: [notes]. Add it to my case study journal under the right heading: Problem, Research, Decisions, Iterations, or Results.
  • Write a component spec for [component]: anatomy, states, behavior, accessibility notes, and content guidelines.

Stay current with research prompts

Turn on Research or web search so answers come with sources. Open the links that matter before you repeat a claim.

  • Research what has changed in [design topic] over the last [time period]. Give me 5 notable developments, each with a real example and a source link. Flag anything that looks like hype.
  • Compare how [company A], [company B], and [company C] handle [pattern, e.g. onboarding]. Summarize what each does well and what I could borrow.

Glossary

Plain-English glossary

The words you'll meet most often, explained without jargon. Git terms are in Frame 02.

Prompt
The message you send Claude. A good prompt reads like a design brief.
Context
Everything Claude can see while it answers: the conversation so far, attached files, and Project instructions.
Model
The AI system behind Claude. Anthropic releases new models over time, and the app picks a sensible default.
Artifact
Something Claude makes that opens in its own panel, like a web page, document, or diagram. You can publish it and share the link.
HTML
The structure of a web page: headings, paragraphs, images, and buttons.
CSS
The styling of a web page: color, type, spacing, and layout.
JavaScript
The behavior of a web page: what happens when someone clicks, types, or scrolls.
Responsive
A layout that adapts to any screen size, from phone to desktop.
Accessibility and WCAG
Designing so people with disabilities can use your work. WCAG 2.2 AA is the standard most teams aim for.
Static site
A website made only of files like HTML, CSS, and images, with no server code. Ideal for portfolios.
GitHub Pages
GitHub's free hosting for static sites, published straight from a repository.
Markdown
A simple way to format plain text, using # for headings and - for lists. READMEs use it.
Terminal
A window where you type commands instead of clicking. Optional for everything in this playbook.
Code editor
An app for editing code files, such as VS Code. It's to code what Figma is to design files.
Connector and MCP
A connector links Claude to another app, like Figma or Google Drive. MCP is the open standard connectors are built on.
Usage limits
How much you can use Claude in a set time window. Long chats and big files use more, and Max raises the limits.
Skill and plugin
A skill is a saved set of instructions that teaches Claude a way of working, like a design review. A plugin packages skills so you can add them to Claude Code with a couple of commands.
Spec
A short written plan: what you're building, why, and how you'll know it's done. Agent Skills' /spec writes one with you before any code.
